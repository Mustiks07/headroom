Сохрани исправления интегратора: 2027 QBI $415 при qualifying QBI $1,030, реальные source links, обновление Marketplace при изменении прогноза, блокировку неподдержанных ranges. Твоя зона: `src/lib/engine`, `data/rules`, `data/reference`, `reference`, `scripts/reference`, `tests/engine`; документация методов и handoff. Не переписывай UI/backend/shared contracts без предварительно описанного аддитивного соглашения.

## Приоритеты

1. **Сверить оставшиеся правила с первоисточниками.** 2027 single/MFJ brackets и standard deduction интегратор уже сверил. Перепроверь QBI minimum как правило целиком, tax-table rounding, SEHI/PTC допустимое решение, ACTC/CTC и календарные сроки в реально поддерживаемом диапазоне. Для каждого найденного расхождения — конкретный воспроизводимый случай, официальный URL/раздел, исправление и одна содержательная регрессия. Не расширяй поддержку низких доходов, EITC или новых форм, пока целиком не реализована соответствующая логика.
2. **Диапазоны должны означать именно обещанное.** Текущая модель двигает profit/interest диапазоны вместе и не проверяет все независимые комбинации. Интегратор запретил payroll/SEP/coverage ranges: иначе нарушается монотонность или диапазон просто игнорируется. Реализуй обоснованную проверку независимых разрешённых диапазонов либо сохрани честное ограничение и выдай точное описание проверенной области. Не используй слово guaranteed/robust для непроверенных комбинаций. Для wages нужна согласованная модель Box 1/3/5/gross/pretax, а не независимое движение пяти несовместимых чисел.
3. **Не замещать старое решение новым незаметно.** Сейчас после изменения дохода scenario kind `split_payment` оптимизируется заново. Для повторной ценности полезно отдельно вычислять последствия уже согласованных receipts/expenses/SEP и затем предлагать новый вариант. Спроектируй и реализуй чистую функцию оценки фиксированных решений, использующую те же guards и правила. Расширение интерфейса сначала опиши в handoff; существующие entry points не ломать. Если исходное действие уже невозможно, объясни почему.
4. **Поиск и выполнимость.** Проверь minimum SEP, split и counteroffer на внутренних порогах, округлениях и user limits. Докажи заявленную точность либо ослабь формулировку; не называй найденную на grid цену гарантированно минимальной без основания. Учитывай реальную дату расходов, следующий год, кассовый бюджет и минимум желаемого дохода. Для split по двум годам checklist должен описывать обновление обоих прогнозов, а не только 2026.
5. **Trace и английские объяснения.** Все годовые числа в пояснениях брать из соответствующего rule pack (не хардкодить 2026 в описании 2027). Понятные названия человека и поля вместо `primary`, `w2Box1`, технических кодов в пользовательском тексте; машинный path/code сохраняй отдельно. Синтетические examples и draft sources остаются явно обозначены. Источники должны быть связаны с реально применённым правилом.

## Как закончить

Не начинай с написания десятков тестов. Сначала проверь конкретные спорные случаи и исправь найденное; используй уже имеющиеся bounded groups. Один итоговый typecheck, затронутые проверки и build. Отдельно выпиши unsupported cases и любые изменения sample numbers. Не подгоняй engine под старую картинку/сумму.

Обнови версии при изменении правил или результатов. Запиши `docs/handoffs/claude2-round2.md`: что исправлено, первоисточники, новая публичная функция фиксированных действий, ограничения, проверка. Commit и push в `claude2`. Main не менять самостоятельно. Никаких заявлений о CPA review или гарантированной экономии без фактов.
