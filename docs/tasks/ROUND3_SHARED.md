# Round 3: one household plan that stays useful

Старт: интегрированный `main` после round 2, engine 1.1.1 / rules r3. Эта спецификация описывает **следующую работу**, не текущие возможности. Все три разработчика сначала читают её и `docs/handoffs/integration-round2.md`.

## Зачем этот раунд

Headroom помогает семье с переменным самостоятельным доходом понимать субсидию и принимать выполнимые решения. Повторная ценность возникает, когда новая оплата, заказ или уточнение прогноза меняет **тот же** семейный план. Сейчас есть хорошие отдельные расчёты; следующий результат — связать их без повторного учёта денег.

Два обязательных входа: «проверить мой годовой прогноз» и «проверить новый заказ». Не заставлять пользователя выдумывать заказ ради проверки субсидии. Сохранить текущие три demo, отсутствие регистрации и весь путь без ключей.

Один демонстрационный сценарий раунда:

1. Пользователь собирает годовой прогноз из уже заработанного и ожидаемого остатка года; видит источники и неизвестные данные.
2. Сохраняет согласованный заказ A и его платежи. Закрывает/открывает браузер.
3. Отмечает фактический платёж A и фактический взнос SEP с суммой/датой.
4. Добавляет предложение B. Headroom оценивает B **поверх A**, сохраняет уже полученные деньги и выполненные действия.
5. Уточняет другой доход. Видит результат старых договорённостей, возможное нарушение плана и отдельно новые варианты.
6. Сохраняет обновлённую версию и скачивает понятное объяснение годового прогноза с фактами, предположениями и источниками.

## Инварианты общей модели

Добавить `HouseholdWorkspace` с собственной `workspaceVersion: "2.0"`, id, revision, timestamps, household profile, annual forecasts, projects, retirement records, evidence и revision history. Точное TypeScript/Zod представление закрепляет первый контрактный коммит; ниже обязательная семантика.

### 1. Один источник годовой прибыли

- На человека/год ровно один активный способ ввода: `annual_total` **или** `year_to_date_plus_remaining`. Между ними явное переключение с подтверждением; не складывать оба.
- `annual_total` — прогноз чистой прибыли **без платежей и расходов управляемых здесь проектов**.
- Составной вариант: подтверждённая дата `asOfDate`, фактическая net profit YTD, ожидаемые оставшиеся gross receipts и ожидаемые оставшиеся deductible expenses. Все три также исключают управляемые проекты. Итог = YTD net + remaining receipts − remaining expenses.
- Фактические YTD расходы уже включены в net profit; второй раз не вычитать. Даты будущей части после as-of и внутри года. Неполная часть — unknown, не ноль. Источники/статус/диапазон сохраняются.
- UI явно спрашивает, включены ли уже проекты A/B в введённую сумму. Пока исключение проектов не подтверждено, не выдавать готовый результат. Продукт помогает исправить вход, не просто прячет предупреждение.
- `CaseInput.years[].incomes[].scheduleCProfit` в новом пути **производное** значение адаптера, не второй независимо редактируемый итог. Остальные доходы/страховка используют существующие проверенные факты.
- Диапазоны суммируются с правильными знаками: low profit = low receipts − high expenses, high profit = high receipts − low expenses. Ни одному документу не назначать период/год автоматически без подтверждения.

### 2. Проекты и платежи

- У проекта стабильный id, владелец, title и состояние proposed/agreed/cancelled. У каждого платежа/расхода стабильный id, evidence, ожидаемые amount/date и отдельные фактические amount/date либо cancellation. Статус проекта не стирает полученные ранее деньги.
- В прогнозе фактическое значение **заменяет** ожидаемое для той же записи. Не прибавлять их. Повторное подтверждение/импорт той же записи идемпотентно; предложить разрешение совпадения, не сливать похожие платежи молча.
- Согласованные проекты входят в текущий прогноз, proposed — только в what-if, отменённые будущие платежи исключаются. Уже полученные платежи остаются даже после отмены проекта.
- У выбранного нового предложения B baseline = семейный прогноз + остальные обязательства; сценарий B добавляет **только B**. Для редактирования A старый A сначала исключается из baseline. Отказ от B не отменяет A.
- Полученный или конструктивно доступный платёж нельзя переносить новым оптимизатором в январь. Отдельно показывать исправление ошибочной записи факта (с историей) и новое соглашение о ещё не выполненном платеже.
- Продолжить использовать существующие guard/SEHI/PTC/year calculations. Несколько проектов одного бизнеса не означают поддержку нескольких Schedule C или S corp.

### 3. SEP — общий годовой лимит, реальные выполненные суммы

- Взносы принадлежат owner + tax year, не каждому проекту. Фактическая запись содержит id, amount, paid date, tax year и evidence; два разных взноса суммируются, повтор записи — нет.
- Годовая цель взноса и сумма уже внесённого различаются. Осталось внести `max(0, target − actual paid)`. Снижение цели не отменяет реально внесённое и не создаёт «возврат денег».
- Невыполненные принятые обязательства по SEP учитываются в общем плане. Новая рекомендация — прирост общей цели, а не второй полный взнос поверх первого.
- Доступные для будущих взносов деньги — явно введённый общий бюджет на оставшуюся часть рассматриваемого периода. Зарезервированные невыполненные взносы уменьшают его; фактически внесённое до ввода этого бюджета не вычитать второй раз. Проверить и общий бюджет, и юридический лимит каждого года.
- Старое v1 поле `existingSepContribution` нельзя автоматически превратить в подтверждённую оплату: при миграции спросить, что уже внесено и что было только планом. То же относится к checkbox «done»: это не документ о сумме платежа.

### 4. Результат, сохранение, происхождение

- Результат отдельно содержит current household projection, fixed agreed plan evaluation и candidate comparison. Новые оптимальные суммы не заменяют согласованные без подтверждения.
- Версионировать входы, engine/rules и fingerprint; включать в него реально влияющие события. Порядок записей при неизменном смысле не должен менять суммы. UI не вычисляет налоги.
- Новый API должен сохранять различие `ready`, `needs_data`, `unsupported`. Удобные названия entry points: `buildHouseholdProjection`, `evaluateHouseholdWorkspace`, `compareWorkspaceOpportunity`; окончательные signatures — в contract handoff. Финансовую реализацию пишет Claude 2, transport/storage — Claude 3.
- Миграция v1 — preview и явное подтверждение, исходный snapshot сохранён. Старые JSON остаются читаемыми. Никогда молча не включать старый проект два раза или не очищать данные при сбое миграции.
- Guest local путь завершён без Supabase/AI. Cloud ошибки явно различают сохранённую версию, не записавшееся событие и несохранённые изменения. Не утверждать cloud sync при local save.

## Ограниченный объём, сильный результат

Сначала закончить этот сквозной сценарий. Не добавлять по пути все штаты, новые tax entities, HSA/Solo 401(k), банковский автоконнект, автоматическую подачу Marketplace-заявления, чат как основной интерфейс или обязательную оплату. Calendar reminders и cash-by-date допустимы следующим этапом после реальной модели фактов; текущий cash after settlement нельзя переименовать в банковский остаток сегодня.

Экспорт называется **Annual income forecast explanation**. Если нет подробной полной книги доходов/расходов, не называть его complete self-employment ledger, официальной формой или гарантированно принимаемым подтверждением Marketplace.

## Конечная проверка

Проверять реальные способы ошибиться: double count A/B; actual вместо expected; исполненный SEP против новой цели; YTD + остаток; v1 migration; ошибка после частично успешного save. Несколько осмысленных проверок, не сотни дублирующих тестов. Typecheck, затронутая группа tests, один build; browser journey для UI. При зелёных проверках не запускать их бесконечно.

Handoff каждого: что закончено, контракт/SHA зависимости, реальные команды и результаты, оставшиеся ограничения, пути screenshots/exports. Commit и push в свою ветку. Готовность — работающий результат, не только типы и заглушки.
