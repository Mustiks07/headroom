# Claude 1 — цель семьи → условия заказа → действие

Прочитать `AGENTS.md`, [общий brief](ROUND4_SHARED.md), [review раунда 3](../handoffs/integration-round3.md). Ветка `claude1`, отдельный worktree/clone, обычный merge свежего `origin/main`. UI, components, features и browser journey — твоя зона; налоги и persistence не дублировать.

## Что сделать

1. **Goal-first сравнение в household workspace.** Из “New client offer” или пересмотра неоплаченной части открыть компактную форму: сколько хочется оставить после обоих налоговых расчётов, ограничение SEP, нужна ли оплата к дате. Дать ясный выбор смысла датированной цели, определённого общим контрактом. Расширенные ограничения раскрываются по необходимости. Полученный аванс виден как фиксированный.
2. **До трёх осмысленных карточек.** Например: “More money by your date”, “More cash overall”, “More room if income rises”. Показывать только реально вычисленные различные варианты; если один лучший — одна карточка. Для каждого: предлагаемая цена, даты/суммы платежей, дополнительный SEP, cash delta, дата/горизонт, условия. Одна короткая причина выбора. Показать цену упрощения, если почти равнозначный вариант требует меньше действий.
3. **Когда не получается.** Отдельные экраны missing facts, unsupported и no feasible terms. Конкретное ограничение и рассчитанный способ его ослабить, если такой есть. Не рисовать успешную зелёную карточку при невыполненной цели. При неполном бюджете показывать только разрешённый contract результат, без «вам хватит на жизнь».
4. **Понятные деньги по датам.** Небольшая временная шкала/сравнение показывает подтверждённые и ожидаемые потоки, резерв и уровень полноты. Уже полученное не превращать в будущий приход. Итог после налогов подписывать отдельно. Без ввода семейного cash context не открывать огромный обязательный budget onboarding.
5. **Что меняет ответ.** Одна раскрываемая карточка с реально найденным ближайшим порогом/значимым неизвестным фактом. Из неё перейти прямо к нужному полю. Сравнение до/после не заменяет согласованный план само.
6. **Выбор → действие.** Подключить action-package Claude 3: preview/copy/download черновика клиенту, calendar, PDF. Пользователь явно подтверждает согласованные условия; сообщение не отправляется автоматически, согласие клиента не имитируется. Устаревший результат пересчитать до применения.
7. **Возврат в продукт.** На household overview короткое “What needs attention next”: конкретное невыполненное действие из текущего результата, выполненные факты, изменение плана. При платеже/SEP обновить остатки; после reload всё сохраняется. Старый v1 demo и текущие маршруты продолжают работать.

## Порядок и зависимости

Не ждать всего backend. Сразу подготовить оболочку с typed props, состояния и английский текст; затем merge маленького `round4-contract` коммита Claude 3. Финальная интеграция использует реальные функции Claude 2/3. Допускается изолированная synthetic fixture для разработки компонентов, но не скрытый fake success в пользовательском пути.

Согласовать с Claude 3 через handoff названия export hooks и действия; не писать свою localStorage-схему. Точечные additions в shared types делает Claude 3 отдельным коммитом. При profile/fact edits сохранять workspace history и stable IDs; неподдерживаемая смена налоговой ситуации должна честно блокироваться.

## Готово, когда

- В реальном браузере человек меняет цель/дату/SEP, получает другое обоснованное предложение, выбирает, скачивает действия, записывает платёж, перезагружает план.
- Невозможная цель и неполные данные выглядят как законченные пользовательские состояния; введённый текст не теряется при ошибке.
- Нет горизонтального скролла на 360 px; keyboard focus/labels читаемы. Первый экран понятен без расшифровки MAGI/APTC.
- Проверены desktop/mobile скриншоты именно текущего production build. Никакой рекламы неработающей функции на landing/pricing.
- Typecheck, релевантный UI smoke, один build. Handoff `docs/handoffs/claude1-round4.md`, commit + push `claude1`. Codex объединит main.
