# Claude 2 — correct combined household decisions

Ветка `claude2`. Fetch + обычный merge `origin/main`, `npm ci`; прочитай AGENTS, [shared brief](ROUND3_SHARED.md), [integration review](../handoffs/integration-round2.md). В main engine 1.1.1/r3, валидация AgreedPlan и исправленная атрибуция 2025 Tax Table. Сохрани эти изменения.

## Сделать

1. **Чистая агрегация прогноза.** По контракту Claude 3 реализовать `buildHouseholdProjection`: annual total либо YTD + остаток, диапазоны с правильными знаками, evidence/status, фактическое вместо ожидаемого, approved projects поверх baseline. Runtime guard для неоднозначного включения проектов. Не превращать missing в zero. Полностью отделить от React/storage.
2. **Проверка B с учётом A.** `compareWorkspaceOpportunity` оценивает только прирост от выбранного кандидата на фоне других обязательств. Если редактируется A, сначала убрать прежний A из base. Отмена B не отменяет A; отмена проекта не убирает уже полученные платежи. В trace должно быть видно, откуда итоговая прибыль каждого года.
3. **Единый SEP.** Фактические owner/year contributions и годовая цель, остаток, общий доступный бюджет будущих взносов. Не учитывать старый взнос дважды, не предлагать перенос внесённого и не считать пенсионные деньги spendable. Проверять лимит на общей годовой прибыли, а не отдельно для A/B. Сначала все уже принятые обязательства, затем допустимый прирост цели для кандидата.
4. **Фиксированный годовой план.** `evaluateHouseholdWorkspace` возвращает результат существующих договорённостей независимо от их оптимальности. Полученный/доступный платёж не может стать будущим предложением переноса. Снижение available cash ниже невыполненного обязательства — явная infeasibility, не молчаливое изменение суммы.
5. **Не потерять математику round 2.** Использовать те же guard/year/SEHI/PTC функции, единый rounding, версии и источники. V1 API оставить совместимым. Новый engine version при изменении результата. Новый fingerprint покрывает события и факты, влияющие на расчёт; API/UI потребляют один результат, не пересчитывают отдельно.
6. **После рабочего engine — конкретное сравнение с конкурентами.** В `docs/research/competitor-workflow.md` записать воспроизводимый сценарий: семья, два года, ограниченный SEP, уже согласованный A, новый B, затем оплаченный SEP и исправленный доход. Проверить доступные официальные функции MyTaxQuarter, ACAIndex, Bracketsight, ProjectionLab. Найти доступные публичные репозитории/демо соперников Business Cup и релевантных Devpost-проектов; если списка или доступа нет, честно ограничить охват. Ссылки, дата, что реально выполнено/что только написано/что нельзя проверить без оплаты. Оценивать по пяти критериям конкурса, отдельно продуктовую конкуренцию и конкурсные проекты. Не выдавать закрытую функцию за отсутствующую, не утверждать, что бесплатные конкуренты не знают SEP/SEHI. Не подписываться и не платить. Не копировать их код/оформление и не запускать непроверенные install/scripts чужих репозиториев.

## Ограниченная проверка

Обязательные группы: два проекта без double count; actual заменяет expected; cancellation сохраняет прошлый receipt; частично внесённый SEP и смена цели; low/high forecast bounds; старое соглашение теряет субсидию при новом доходе; без изменений входов результаты round 2 сохраняются. Минимальные понятные контрпримеры, одна проверка каждого класса ошибки. Typecheck, relevant tests, один build — без coverage гонки.

Твоя зона — engine и финансовые reference/tests. Shared schema owner Claude 3; UI owner Claude 1. Сразу после контрактного коммита согласуй signatures в handoff, не делай отдельный несовместимый Workspace type. Не добавлять новые налоги/все штаты ради масштаба этого раунда.
