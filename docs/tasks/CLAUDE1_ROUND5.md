# Claude 1 — законченный пользовательский путь с минимальным ручным вводом

Ты отвечаешь за интерфейс, понятность и первое впечатление Headroom. Не ограничивайся прикручиванием чата к прежней длинной форме. Сделай продукт, которым человек без знания ACA/MAGI может воспользоваться и к которому имеет смысл вернуться.

## Старт и границы

В своём clone на `claude1`: `git fetch origin`, обычный `git merge origin/main`, `npm ci`. Прочитай `AGENTS.md`, `docs/handoffs/integration-round4.md`, `ROUND5_SHARED.md`, это задание, текущий `TZ.md`. Первый shared-contract commit ждём от Claude 3; бери его по SHA. Не жди весь backend: сначала проработай путь, компоненты и независимые ручные состояния.

Твои пути: `src/app/**` кроме API, `src/components/**`, `src/features/**`, `public/**`, UI smoke, design/demo copy. Не меняй финансовые формулы, shared schemas, серверные env или Supabase. Если нужна операция — согласуй контракт с Claude 3/2, не создавай похожую локальную модель.

## 1. Перестроить первый вход вокруг задачи

Первый экран коротко отвечает: для кого, какой результат, как попробовать. Основные входы: **“Check a client offer”**, **“Check my year's income”**, **“Try a sample”**. Названия уточни по живому пути. No account wall. Сохранённый household открывается сразу; не спрашивать заново уже подтверждённые сведения.

Дай выбор “Upload documents / Paste text / Enter figures”. Разреши начать с предложения клиента, даже если household ещё не готов: сохранить черновик предложения, затем получить только нужные факты семьи. Не обещать точный результат до достаточных данных. Демо показывает тот же живой движок, а не записанные числа.

Пусть первый полезный экран появляется до большой анкеты: что уже известно из предложения/документов, что надо уточнить, зачем. Счётчик остающихся вопросов допустим только по фактическому readiness; не писать выдуманное “2 minutes” без измерения.

## 2. Документы как основной способ заполнения

Переиспользуй `features/household/DocumentImport.tsx`, `extractDocument`, `previewDocumentFacts`/`applyDocumentFact` и новый контракт. Не делай второй upload pipeline. Поддержи поочерёдно несколько документов без потери предыдущего черновика: понятные статусы waiting/reading/review/needs clarification/failed.

Карточка факта: понятное название, сумма/дата, человек, год и период, откуда прочитано, подтверждено ли пользователем. Источник можно раскрыть; для страницы документа показать ссылку/preview при наличии разрешённого локального файла. Не показывать внутренние JSON paths как основной текст.

Разреши подтвердить группу согласованных фактов одной кнопкой после обозримого summary. Конфликтующие значения, unknown person/year/period, gross vs net, received vs invoiced — отдельный выбор. Никакого десятка одинаковых кликов по бесспорным значениям и никакого молчаливого “confirm all” спорных полей.

При сбое/лимите/нечитаемом файле сохранить уже введённое и предложить корректировку/ручной ввод. Если AI off, честно сказать, какие форматы доступны; не показывать фальшивый прогресс OCR. Не требовать W-2/1095-A за ещё не завершившийся год. Consent относится к конкретной передаче провайдеру, а не к скрытому общему согласию.

## 3. Короткое дозаполнение

Используй `InputReadiness` Claude 2. Показывай 1–3 логически связанных вопроса, не всю техническую модель. У каждого: почему нужен, пример и “I don't know yet”. Для текущего года не спрашивать 2027. Для timing across years объяснить, почему второй прогноз теперь нужен.

Неизвестный доход супруга ≠ ноль. Если пользователь подтверждает отсутствие дохода, это отдельное осознанное действие. При наличии monthly policy values дать явное “Same every month” вместо 12 одинаковых ручных строк, но сохранить возможность разных месяцев и не расширять full-year eligibility scope.

Редактирование полного household остаётся доступным. Новая короткая форма не должна обрезать сведения старых сохранённых планов. Черновик переживает reload; отмена импорта не затирает введённое.

Убрать требование знания FIPS: обычный выбор штата/округа, ZIP только с разрешением неоднозначности, служебный код скрыт. Для insurance facts добавить “Help me find this”: показать нужную строку/колонку документа и полученное значение, различить enrollment premium, benchmark и APTC. Подключить verified lookup Claude 2/3 там, где есть данные. Если точного значения нет — явно county candidate/unknown и адресный следующий шаг; не средняя цена, замаскированная под точную. Этот участок особенно важен: AI не устранит manual friction, если после чтения документов человек всё равно не знает, где взять benchmark.

## 4. Предложение клиента → решение

Вставка письма/текста оффера или документа должна создавать обозримый draft проекта: total price, already received, unpaid schedule, expenses, negotiability, receipt conditions. Счёт сам по себе не является подтверждением оплаты. Предложение клиента не подтверждает, что он согласен на наши новые условия.

Сохранить сильные элементы round4: цель чистой прибавки денег, срок, SEP cap, максимум три различающихся варианта, условие изменения выбора. Сначала человеческий вывод, затем число, затем следующий шаг; таблицы/точность поиска/полная налоговая трасса раскрываются по запросу.

Price bounds — ПОЛНАЯ цена включая аванс. Не возвращать ошибку “unpaid price”. Варианты должны ясно различать деньги к сроку, итог после двух деклараций и пенсионный капитал. Не отображать весь остаток семьи по неполному cash context. Для household balance дай компактные существенные входящие/исходящие движения (существующий typed contract), либо держи этот режим неполным.

## 5. Обновление фразой и объяснения

На household — заметный “What changed?” с примерами: “The final payment will arrive on January 8, 2027”, “I received $3,200 today for the bakery project”, “I contributed $1,500 to my 2026 SEP”. Отправляет текст в Claude 3 API, не выполняет самостоятельно.

Preview показывает проект/строки, старое → новое, что считается подтверждённым, последствия по engine Claude 2. Если два подходящих проекта/неясный год/дата — короткий вопрос выбора. Кнопки Apply / Edit / Cancel. После Apply — одна ревизия, пересчитанная текущая позиция и конкретное изменившееся действие. Повтор не удваивает платёж.

“Why this option?” отвечает проверенными фактами: относительно чего сравнили, почему вариант подходит, что усложняет его и что меняет ответ. Не показывать свободно сгенерированные налоговые советы или число “confidence 97%”. Подробные источники доступны отдельно.

Не смешивать “what this project leaves you” с “improvement over the original offer”. Подключить обе базы и reason recommendation от Claude 2. Если лучший cash требует более высокой цены/новых сроков, явно показать зависимость от согласия клиента и исходный вариант рядом. Хрупкий план с $1 запасом не получает зелёную метку безопасности. Минимальное достаточное изменение при заданном запасе и максимальные условные деньги — разные варианты, а не две одинаково настойчивые рекомендации.

## 6. Завершить исполнение, а не оставить пользователя с карточкой

После согласия клиента можно открыть/скачать исторический пакет и отдельно свежую оценку. Подключи новый export contract Claude 3; не обходи запрет stale exports присваиванием нового fingerprint старым цифрам. Исторические суммы имеют дату/ревизию/явную подпись.

Attention list: неоплаченные строки, реальное изменение риска, вклад SEP, несогласованные предложения, ближайшее выполнимое действие. Убрать дубликаты и уже выполненные напоминания. “Mark done” ≠ записать финансовый факт без суммы/даты. Не обещать email/push, пока их нет. Календарь скачивается в браузере.

Разные сценарии должны быть согласованы: согласие, оплата, изменение прибыли, возврат через неделю, экспорт/restore. Переходы не теряют источник, аванс, историю или выбранные условия.

## 7. Конкурсное впечатление и измерение

Проверь главную, обычный и cliff-сценарий, mobile360, пустые/ошибочные состояния, loading/disabled, focus/keyboard, labels/contrast. Спокойная ясная английская речь. Убрать дублирующие CTA и внутренние названия полей; не маскировать ограничения длинным disclaimer.

Собери `docs/demo/round5-judge-script.md`: реальный 90–120-секундный маршрут с проверяемыми результатами, альтернативный путь при отсутствии provider, где показать отличие от бесплатного калькулятора. Это сценарий, не выдуманное видео. Приложи скриншоты именно финального build. Готовые материалы пользователя не заменять.

Добавь согласованные с Claude 3 неперсональные funnel events в ключевых переходах. Отделять synthetic demo/own input, new/returning workspace. Не передавать text/amount/document/household profile. Обнови дизайн/copy docs, но README с live feature claims правит Codex после проверки публикации.

## Приёмка и handoff

Перед handoff добавь короткий продуктовый пакет `docs/demo/round5-positioning.md`: основной сегмент, повод открыть сегодня, за какой завершённый результат человек мог бы платить, повод вернуться; две альтернативные формулировки лендинга и три рекламные концепции как НЕЗАПУЩЕННЫЕ drafts. Используй выводы исследователя, если уже доступны. Для каждой концепции укажи pain → promise → proof in product → CTA. Нельзя рисовать реальные CTR/CAC или отзывы. Не меняй публичный тариф экспериментом наугад и не делай три конкурирующих homepages. Подготовь outline English deck <=10 slides с местами под проверенные evidence и реальные screenshots; это outline, не замена пользовательского финального deck.

Один полный путь документы/вставка → review → missing facts → реальный result → цель → package → client agreement → update phrase → confirmation → reload → export. Отдельно ordinary-positive, ambiguous update и provider unavailable. Проверить desktop и360, реальный PDF/ICS, без overflow/мертвых кнопок. Typecheck, затронутый smoke, build один раз после завершения; повтор только после сбоя/правки.

Commit/push `claude1`. Handoff: `docs/handoffs/claude1-round5.md`, SHA зависимостей, фактические маршруты, количество вопросов/вводимых полей до результата на сценарии, что проверено с реальным provider и что без него, ограничения, артефакты. Не заканчивать на красивых моках или “жду весь backend”: назови конкретный export, а независимые части заверши.
