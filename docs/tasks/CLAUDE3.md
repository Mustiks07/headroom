# Claude 3 — backend, документы, Supabase и интеграция

Ветка: **`claude3`**. Прочитай `AGENTS.md`, `docs/TZ.md`, `docs/ARCHITECTURE.md`, `docs/DEPLOYMENT.md`, `docs/ACCEPTANCE.md` и shared contracts. Работай в отдельной копии, не переключай checkout других разработчиков.

## Результат

Реальное хранение/обновление планов, импорт с подтверждением, PDF/JSON, понятная demo/test оплата и собранное вместе приложение. Ты интеграционный владелец общей версии. **Пользователь ни разу не регистрируется, не входит и не вводит обязательный email/пароль.** Анонимная сессия техническая и невидимая.

## Твои файлы

`src/lib/client/**`, `src/lib/server/**`, `src/app/api/**`, `supabase/**`, `tests/integration/**`, package/config/CI/lockfile; `docs/handoffs/claude3.md`. После foundation ты владелец согласованных изменений `src/domain/contracts.ts` и fixtures. Не меняй их молча; остальные должны получить точное изменение.

## Задачи по порядку

1. Реализовать `createPlanRepository()` для локального браузерного хранения с сохранением после reload, revision conflict, событиями и clear. Не использовать process-memory Map как сохранение между запросами Vercel.
2. Подготовить Supabase adapters, применяемую миграцию и RLS из foundation. При наличии ключей подключить невидимый anonymous sign-in и серверную проверку пользователя. Не доверять owner_id из body. Нет ключей/сессии — полноценный локальный режим с правдивой подписью, без login gate.
3. Реализовать API из ARCHITECTURE. Для расчёта используй тот же engine Claude 2. Перед сохранением/экспортом перепроверь расчёт и chosen scenario, не принимай подменённые клиентом суммы как достоверный финансовый результат.
4. Реализовать реальный импорт CSV/TXT и адаптер PDF/image для предоставленного ИИ-провайдера. Файл/текст — недоверенные данные. Верни предложенные поля, источник и предупреждения; ничего не применяй автоматически. При отсутствии ключей или неподдерживаемом файле честно предложи ручной ввод.
5. Реализовать `exportPlanPdf()` и `/api/export`: readable English report с обоими годами, cash/retirement, assumptions, sources, actions и fingerprint. PDF должен соответствовать свежему расчёту. Не экспортировать старые числа под новой формой.
6. Реализовать capabilities, обработку ошибок/таймаутов и минимальную обезличенную аналитику без сумм/документов. Сырые документы не хранить по умолчанию, секреты не отдавать клиенту. Удаление данных завершает реальное удаление в текущем режиме.
7. Реализовать явно demo checkout без карты. Если предоставлены Stripe test keys, добавить настоящий test-mode flow с корректной серверной проверкой; не выдавать test/demo за выручку. Жюри проходит весь продукт независимо от оплаты.
8. После хэндоверов Claude 2 и Claude 1 получить их ветки, объединить в `claude3`, устранить стыки. Нельзя оставлять заглушки в основной цепочке или рисовать mock results из-за неудобного контракта.
9. Пройти конечный acceptance list, собрать production build, подготовить Vercel подключение. Когда проект/ключи доступны, проверить именно deployed URL в чистой сессии. Подготовить README со ссылками на реальные артефакты; не придумывать адрес/готовый PDF.

## Ключи и блокировки

Все необходимые имена в `.env.example`; значения пользователь предоставит позднее через настройки среды. Не проси их повторно для работы над локальным хранилищем, API-контрактом и ручным сценарием. В хэндовере перечисли только конкретные недостающие настройки. Отсутствие ключа не повод имитировать AI/cloud success.

Если тип ИИ-провайдера ещё не известен, оставь интерфейс адаптера и полноценный ручной путь, подготовь один выбранный провайдер с явным требованием его ключа. Не делай три параллельные дорогостоящие интеграции без нужды.

## Порядок интеграции

Сначала fetch, проверить чужие handoff и diff. Merge `origin/claude2`, затем `origin/claude1` в свою ветку (порядок можно поменять при зависимостях). Не cherry-pick чужой foundation второй раз и не force push. Устранить конфликты по владению: финансовая семантика — Claude 2, продуктовый UX — Claude 1, общий контракт — согласованное решение.

В общий `main` передавать интегрированный результат через понятный PR/merge после конечной проверки. Не публиковать финальный сайт, README или deck с заглушками и не заменять пользовательский финальный материал более слабым автоматически сгенерированным файлом.

## Проверки и хэндовер

Один local round trip; один two-user RLS/ownership check после подключения Supabase; один реальный импорт и один отказ; один PDF с проверкой содержания; три пользовательских сценария на общей сборке. После зелёных проверок завершить интеграцию. Расширять проверки только из-за найденного дефекта/нового изменения.

`docs/handoffs/claude3.md` содержит применённые миграции, env names без значений, провайдеры/режимы, реально проверенный public URL/commit, результат acceptance, оставшиеся внешние блокировки. Не заявлять работающий Supabase или ИИ до фактической проверки.
