# Claude 1 — интерфейс и полный пользовательский путь

Ветка: **`claude1`**. Работай в отдельном clone/worktree. Прочитай `AGENTS.md`, `docs/TZ.md`, `docs/DESIGN.md`, `docs/ARCHITECTURE.md` и `src/domain/contracts.ts`. Это уже общий проект; не запускай create-next-app и не создавай отдельный frontend.

## Результат

Пользователь понимает исходную задачу — защитить субсидию на медстраховку — и проходит от своих данных до сохранённого обновляемого плана. Интерфейс и весь генерируемый пользовательский текст на английском. **Никаких экранов входа, регистрации, обязательного email или оплаты.**

## Твои файлы

`src/app/**`, кроме `src/app/api/**`; `src/components/**`; `src/features/**`; `public/**`; небольшой UI smoke flow. Свой отчёт: `docs/handoffs/claude1.md`. Не меняй движок, серверные адаптеры и схему БД.

## Задачи по порядку

1. Заменить стартовую developer-страницу нормальным первым экраном Headroom. Основной CTA — Check my subsidy, демо рядом, новый заказ как дополнительный вход. Выбор демо сразу открывает редактируемый рабочий сценарий.
2. Сделать понятную форму семьи: штат, статус, члены семьи/страхуемые, доходы каждого супруга, текущая страховка. Скрывать нерелевантные подробности, но не подставлять нули в неизвестные поля. Явное «нет такого дохода» может подтвердить нулевое значение. Факты и источники редактируемы.
3. Подключить `assessCurrentRisk(input)`: текущая субсидия, MAGI/порог, возможный возврат аванса, доступный запас дополнительной прибыли с условиями. Не требовать новый заказ или известный следующий год для этой первой проверки.
4. Добавить предложение/изменение дохода и сбор следующего года только при переходе к нужному сравнению. Отдельно сумма заказа и расходы с датами.
5. Подключить `calculateComparison(input)`: карты вариантов, оба года, видимая база сравнения, отдельные доступные и пенсионные деньги. Данные только из результата. Контролы бюджета SEP/сроков/цены реально вызывают пересчёт. Не ранжировать самостоятельно по придуманной формуле.
6. Сделать drawer источников/расчёта и состояния needs_data/unsupported. При редактировании убирать актуальность старого объяснения до нового результата. При недоступном engine показывать его реальный статус, не подставлять goldens.
7. Через `extractDocument` показывать просмотр и подтверждение каждого извлечённого поля. Ручной ввод остаётся полноценным. Не обещать, что неизвестный файл прочитан, если сервер вернул unavailable.
8. Реализовать выбор и страницу плана через `createPlanRepository()`, статус локального/облачного сохранения, список действий, подтверждение выполнения, Something changed, историю изменений, очистку данных.
9. Подключить PDF через `exportPlanPdf`, JSON экспорт/импорт через общий контракт, pricing $99/year per household и явно демонстрационный checkout. Весь путь доступен жюри без карты и аккаунта.
10. Проверить мобильный/desktop путь, ошибки и клавиатуру. Удалить developer-copy из релизного пользовательского пути только когда соответствующие функции действительно подключены.

## Как работать параллельно

Общие entry points уже существуют. На своей ветке они могут возвращать unavailable до интеграции Claude 2/3 — это нормально для разработки, но не критерий завершённого релиза. Не реализуй второй движок/временную формулу. Можно строить визуальные состояния на typed fixtures в отдельной development-only истории, но не выдавать их за рабочий результат в публичном сценарии.

Стабильный интерфейс к расчётам и хранилищу описан в ARCHITECTURE. Для расширения общего типа оставь конкретное предложение в handoff; согласуй с Claude 3 до изменения, чтобы обе стороны совпали. UI-only зависимости/конфиг — через интеграционного владельца, без второго lockfile.

## Приёмка твоей части

Три сценария из ACCEPTANCE, отсутствие регистрации/входа, English everywhere, неразрушающее исправление полей, отсутствие выдуманных чисел, реальные точки подключения сохранения/экспорта. Риск здоровья/страховки остаётся центральным, приложение не превращается в обычный budget dashboard.

После изменения запусти typecheck и один build, плюс один относящийся к пути smoke check, когда зависимости интегрированы. Не пиши десятки тестов на тексты/цвета. Хэндовер содержит маршруты, законченные состояния, необходимые подключения, реальный результат проверки и оставшиеся проблемы.
